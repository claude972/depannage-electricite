# QA-ADV-ROLLBACK-001 — recette SQL réelle sans fixture persistante

Branche `claude/web-pwa-backend` (worktree `depannage-claude-backend`), base `d7abd8c` + fusion de `origin/integration/web-pwa` (`4506033`, migrations 014–017 revues) pour l’exécution locale. **Contrat publié avant le code.** Périmètre exclusif : `scripts/qa-advanced-platform/rollback.sql`, ce document, `tests/sql-adv-rollback-review.mjs` (vérification locale ciblée). Jamais `scripts/qa-advanced/**` (Codex), aucune migration, API, coque ou global modifié. Aucune exécution cloud par cet agent : le pilote exécute le script après revue avec `supabase db query --file` (rôle root/`postgres` du projet dédié, après application de 014–017).

## Objectif

Exercer **les vrais RPC et RLS** des lots finance/plateforme (014), documents de devis (015) et B2B opérations de site (017) sur une base où ils sont appliqués, avec des **comptes synthétiques** dont le JWT est posé localement, à l’intérieur d’**une seule transaction `BEGIN … ROLLBACK`**. Toute écriture (cohorte, dossiers, devis, paiements QA, factures, grants, audit) est annulée par le `ROLLBACK` final : aucun `COMMIT`, aucune fixture permanente, aucun trigger désactivé, aucun compte réel ni e-mail, aucun Stripe. Un super admin **temporaire** est créé puis annulé par le rollback : le garde du dernier super admin (`profiles_last_super_admin`, 014) reste intact et n’est jamais contourné — c’est ainsi que les scénarios admin sont testables après 014 sans aucun bypass.

## Forme du script `scripts/qa-advanced-platform/rollback.sql`

- SQL pur (aucune méta-commande `psql`), un seul fichier, séquence : `begin;` → bornes → préconditions → helpers temporaires → sections de recette → rapport → `rollback;` **inconditionnel** (dernière instruction, hors de tout bloc). Toute exception non attendue dans un bloc `do $$ … $$` fait échouer l’instruction et abandonne la transaction : **aucun critère ne passe silencieusement** ; un échec est un `raise exception … using errcode='QA001'` (code réservé au harnais, distinct des codes métier `P0001`, `42501`, `22023`, `P0002`, `23505`, `53300`, `QD001`).
- Bornes locales : `set local statement_timeout`, `set local lock_timeout`, `set local idle_in_transaction_session_timeout` (valeurs fixées dans le script, révisables par le pilote).
- **Préconditions (refus explicite, `QA001`)** : présence de 014 (`platform_operator_grants`, `platform_access()`), 015 (`quote_documents`, `generate_quote_document(uuid,uuid)`), 016 (`artisan_planning_entries`), 017 (`site_sla_cases`, `site_operations_snapshot(uuid)`) ; capacité du rôle courant à `set role authenticated` / `service_role` (membre ou superutilisateur) ; `auth.users` accessible en insertion. Sans ces conditions le script s’arrête avant toute écriture.
- **Identité par acteur** : `set local role authenticated` (ou `service_role` pour les chemins serveur) + `set_config('request.jwt.claim.sub', <uuid>, true)` **et** `set_config('request.jwt.claims', '{"sub":…,"role":"authenticated","aud":"authenticated"}', true)` — les deux formes que `auth.uid()` de Supabase lit ; même mécanisme que `tests/sql-*-review.mjs`. Aucun secret, aucune clé, aucun JWT signé : les claims sont locales à la transaction. Retour au rôle racine par `reset role` après chaque appel ; les blocs d’attente de refus restaurent le rôle même en cas d’exception.
- **Helpers temporaires uniquement** (`pg_temp.*`, détruits avec la session, jamais dans `public`) : contexte des identifiants, journal de rapport, `qa_as`, `qa_root`, `qa_call` (succès attendu, résultat jsonb), `qa_refused` (code SQLSTATE exact attendu, sinon `QA001`), `qa_check` (assertion booléenne), `qa_note` (`raise notice` borné).
- **Cohorte synthétique** : identifiants `gen_random_uuid()`, étiquette de run `qa-rb-<hex>` dans les e-mails (`qa-rb-<run>-<rôle>@example.invalid`) et les noms (« QA … ») ; insérée dans `auth.users` (colonnes réelles : `instance_id`, `aud`, `role`, `email`, `encrypted_password` aléatoire inutilisable, `email_confirmed_at`, `raw_app_meta_data`, `raw_user_meta_data`, dates) — le trigger `on_auth_user_created` (001) crée les `profiles`. Acteurs : client, autre client, gestionnaire propriétaire d’organisation, viewer, délégué (manager à portée `selected`), artisan, autre artisan, **super admin temporaire** (promotion directe de son seul profil QA par le rôle racine, dans la transaction), opérateurs `finRead`, `finWrite`, `moderator`, `auditor` (jamais `role='admin'`, uniquement des scopes explicites accordés par le super admin temporaire).
- **Jamais une ligne réelle** : toutes les écritures ciblent des lignes de la cohorte (filtres par identifiants QA). Deux exceptions lues honnêtement : les **paramètres plateforme** (`commission_bps`, `invoice_issuer`) sont **lus s’ils existent** (les attentes sur les taux/TVA s’en déduisent) et **créés seulement s’ils sont absents** ; les refus de validation (`22023`) et de version (`P0001`) sont testés sans modifier la valeur. Le rapprochement `platform_reconcile(n)` parcourt les paiements réglés non rapprochés **de toute la base** (`for update`, plus anciens d’abord) : le script lit d’abord `missing_settlement` via `platform_finance_report()` et n’appelle `platform_reconcile` qu’avec `n = manquants + paiements QA` (≤ 500) ; au-delà, il **refuse** le critère (`QA001`, « environnement non rapprochable ») plutôt que de prétendre l’avoir testé. Les agrégats du rapport finance sont comparés **en delta** (avant/après les paiements QA), jamais en valeurs absolues.
- **Données de paiement QA explicites** : les paiements sont créés en `pending` par `service_role` puis réglés par `confirm_stripe_payment` avec des identifiants `cs_qa_<run>_n` / `evt_qa_<run>_n` ; la commission retenue et le remboursement réglé passent par les RPC `service_role` avec des événements `evt_qa_…` simulés. Le rapport le dit en toutes lettres : **aucun fournisseur de paiement n’a été appelé**, un résultat fournisseur positif simulé n’est pas une preuve Stripe.
- **Compteurs de débit QA** : les RPC consomment `action_limits` par acteur et par minute (`create_intervention` 5, `platform_invoices` 20, …) ; une recette complète dépasse ces plafonds pour un même acteur synthétique. Le script remet à zéro, au début de chaque section, les lignes `action_limits` **des seuls acteurs QA** (`pg_temp.qa_reset_limits`, lignes synthétiques annulées par le rollback) ; aucun compteur réel n’est touché et le plafond lui-même est prouvé par le critère 11 (`53300`).
- **Rapport borné** : `raise notice` par critère (`PASS …` / contexte), un résumé final (compte de notes, identifiants de run, nombre de lignes QA créées par table avant rollback) ; jamais de jeton, clé, mot de passe ni donnée réelle.

## Critères de recette (chacun = assertion bloquante)

### 014 — opérateurs, audit, finance
1. `platform_access()` d’un compte sans scope : `super_admin=false`, `scopes=[]`. Clients/gestionnaires/artisans/opérateur sans scope ne peuvent pas accorder (`42501`) ; scope inconnu `22023` ; cible super admin `P0001`.
2. Le super admin temporaire accorde `finance_read`, `finance_write` (finWrite), `reviews_moderate`, `audit_read` ; rejeu d’un grant actif → `replayed=true` ; `has_platform_scope` cohérent ; lecture RLS des grants (chacun les siens, le client aucun) ; `update`/`delete` des grants refusés même par `service_role` (`P0001`/`42501`).
3. Audit : visible par `audit_read` seulement (lignes QA), immuable (`update`/`delete` refusés par opérateur, admin, `service_role` ; par le rôle racine sur une ligne QA → `P0001`).
4. Révocation : `platform_revoke_scope` ferme l’accès immédiatement (rapport finance refusé `42501`), historique conservé, rejeu `replayed=true`. Garde du dernier super admin : `platform_set_super_admin` sur soi-même `P0001` ; démotion directe du **profil QA admin** : si la base ne compte qu’un seul admin (le QA) → `P0001` attendu ; sinon (admin réel présent) la démotion du QA réussit et il est repromu — la branche exécutée est rapportée. Aucune écriture sur un profil réel.
5. Paramètres : `commission_bps`/`invoice_issuer` refusés hors super admin (`42501`), valeurs invalides `22023`, version obsolète `P0001`, lecture RLS (finRead 0, finWrite ≥ 1).
6. Flux métier réel jusqu’au paiement réglé (deux dossiers QA : 300,00 € TTC et un dossier à 100 centimes / TVA 17 pour les avoirs fractionnés) : `create_intervention` (urgence `scheduled`), `accept_mission`, `send_quote`, `accept_quote`, `start`, `complete`, paiement `pending` puis `confirm_stripe_payment` (service).
7. Ledger : `platform_reconcile` refusé sans `finance_write` (`42501`), limite invalide `22023` ; après exécution, le paiement QA porte `payment_settled` (montant/devise/`external_event_id` = session QA) et `commission_estimated` si un taux existe (basis = taux persistant, version) ; rejeu idempotent (aucune entrée ajoutée pour les paiements QA) ; ledger immuable (`42501` opérateurs/admin, `P0001` racine sur une entrée QA). Commission retenue : service seulement (`42501` sinon), statut fournisseur non `succeeded` `P0001`, session/montant/devise incohérents `P0001`/`22023`, enregistrement unique (`true` puis `false`).
8. Remboursements : plafonnés au montant réglé, idempotents par `request_id` (conflit de contenu `P0001`), transitions versionnées (`approve`→ pas de second `approve`, `cancel` libère le montant), règlement service seulement avec événement vérifié (statut, montant, session) → `refund_settled` au ledger. Litiges : `open → under_review → resolved` versionné, demande de remboursement d’un autre paiement refusée.
9. Factures : readiness « données manquantes » explicite (`billing_contact`, `artisan_siret`, `platform_issuer`/`platform_commission_vat_rate`, `commission_not_confirmed` selon l’état), émission refusée tant que non prête (`P0001`), contact de facturation versionné, numéro `F<année>-000001` pour l’émetteur QA (compteur par `issuer_key`, transactionnel), rejeu idempotent, facture de commission avec TVA extraite, avoirs plafonnés **en cumul TTC et TVA** (100 ct / TVA 17 → 33+33+34 créditent exactement 17 de TVA ; avoir au-delà du solde `P0001` ; avoir sur avoir `P0001`), factures immuables.
10. Modération d’avis : masquage réservé au scope `reviews_moderate`, contestation par l’artisan concerné uniquement, décision versionnée, avis masqué retiré de `artisan_performance`, jamais supprimé.
11. Plafonds : `platform_reconcile` sous `action_limits` saturé pour l’opérateur QA → `53300` (ligne `action_limits` QA, annulée).

### 015 — validité, avenants, documents
12. `set_quote_terms` réservé à l’artisan attribué (`42501` tiers/client/gestionnaire/admin), date passée `22023`, état `valid`/`unspecified` ; devis explicitement expiré non acceptable (`P0001`, statut inchangé) ; sans validité jamais expiré.
13. `generate_quote_document` : émetteur incomplet → `QD001` (champ nommé), idempotent par snapshot, nouvelle révision après acceptation, tiers `42501`, téléchargement privé et audité (`P0002` pour un tiers), `quote_documents` invisible aux tiers (RLS).
14. Avenants : proposition par l’artisan attribué sur devis accepté seulement, lignes/taux/motif validés (`22023`), une proposition à la fois (`P0001`), décision par le demandeur uniquement (`42501` sinon), retrait par l’auteur, devis d’origine intact.
15. Accès : après `reassign_intervention` par le super admin temporaire, l’ancien artisan perd terms/overview/generate/download (`42501`/`P0002`) ; le nouvel artisan n’est pas émetteur ; le demandeur garde l’accès. B2B : viewer lit l’overview mais ne génère pas (`42501`), membre retiré perd tout (`42501`/`P0002`).
16. RLS `documents` (001/003/013) : une ligne QA insérée par le rôle racine pour le client est lue par le client et l’artisan attribué, pas par un autre client ; après réaffectation l’ancien artisan ne la lit plus.

### 017 — B2B opérations de site
17. Équipement : création/mise à jour versionnée par un délégué à grant `can_write`, version obsolète `P0001`, charge utile stricte `22023`, historique `site_operations_events` avec snapshot.
18. Matrice de refus : lecteur, viewer, autre site, hors organisation, admin, artisan, site inconnu → `42501` ; aucune écriture directe des tables ni des helpers privés (`so_log`, `so_lock_organization`).
19. Révocation immédiate : grant abaissé puis retiré → écritures refusées, lectures à zéro, snapshot refusé ; retrait de membership → idem.
20. Exercice fiscal (chevauchement `P0001`, durée `22023`, écriture organisation-wide seulement), lignes budgétaires versionnées, consommation d’un devis accepté dans l’exercice (snapshot), grille contractuelle brouillon → publiée → remplacée (publiée immuable `P0001`), calendriers/politiques/cas SLA (chronologie `22023`, pause unique, reprise versionnée, cas résolu figé), checklist ERP déclarative par contrainte, snapshot RLS (grilles `null` pour un membre `selected`, drapeaux d’écriture par acteur, étrangers refusés).

### Clôture

## Limites honnêtes

- Ce harnais local prouve la logique SQL et l’absence de résidu sous PostgreSQL isolé ; il ne prouve pas les privilèges réels du rôle `postgres` Supabase sur `auth.users`, ni `auth.uid()` réel (stub), ni Storage, ni la concurrence multi-sessions, ni un navigateur/HTTP. La preuve réelle est l’exécution par le pilote.
- Les **séquences d’identité** (`platform_audit.id`, `audit_log.id`, `action_limits`, …) avancent de façon durable même après rollback (trous d’identifiants, aucune ligne). Les numéros de facture utilisent un compteur transactionnel (aucun trou).
- `platform_reconcile` verrouille (`for update`) les paiements réels non rapprochés le temps de la transaction (bornes `lock_timeout`) ; aucune modification durable. Si trop de paiements réels sont non rapprochés, le critère 7 est refusé explicitement.
- Les paramètres plateforme existants sont lus, jamais réécrits (sauf tentatives refusées) ; s’ils sont absents, ils sont créés dans la transaction et annulés.
- Un `kill` de la session pendant l’exécution annule la transaction (aucun résidu) ; un arrêt par `statement_timeout` idem.
- Rapport : résultats réellement exécutés par le pilote (sortie `NOTICE`), pas de preuve HTTP/navigateur.
