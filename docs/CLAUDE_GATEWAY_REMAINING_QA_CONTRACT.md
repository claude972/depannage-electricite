## 1. Expiration réelle en deux modes, sans attente bloquante

### 1.1 Principe
Un jeton **réel** d’un **seul** compte client technique est obtenu par password grant, prouvé valide **avant** échéance par une commande **sans mutation**, stocké 0600 hors Git, puis — après que le temps réel a passé — présenté **tel quel** (jamais rafraîchi, jamais re-signé, jamais forgé) à la **vraie** fonction Edge (`verify_jwt: true`) qui doit répondre 401 sans fuite. Aucune lecture du secret JWT, aucune modification du TTL/JWT du projet, aucun `sleep` long : la relance après échéance est faite par l’automation existante du pilote (même commande, mode `verify`).

### 1.2 Interface (additive)
```
node scripts/qa-gateway/run.mjs --suite expiry-prepare --function-url <…/native-document-upload> --project <ref> --credentials <creds.json> --out <dossier privé 0700>
node scripts/qa-gateway/run.mjs --suite expiry-verify  --lease <dossier privé>/lease.json --function-url <…> --project <ref> --credentials <creds.json> --out <dossier privé 2>
```
Sans `--suite`, comportement actuel inchangé (9 scénarios). `--suite` et `--cleanup-manifest` restent compatibles : `--cleanup-manifest` nettoie aussi une cohorte d’expiration (le manifeste porte `suite: "expiry"`). `--dry-run` avec `--suite expiry-prepare` : contrôles d’arguments/projet/santé Auth uniquement.

### 1.3 Mode `prepare`
1. Cohorte **minimale** : **un** compte Auth `qa-gw-exp-<run>@qa.invalid`, `email_confirm: true`, métadonnées `role: client`, créé par l’API admin ; aucun admin, aucune finance, aucun document, aucun dossier, aucun e-mail envoyé. L’**identifiant durable est écrit dans le manifeste avant toute authentification** (manifeste 0600, `suite: "expiry"`, `userIds: [uid]`, `leaseEndsAt`). Le mot de passe (32 octets aléatoires) n’existe **qu’en mémoire** du processus `prepare` : jamais écrit (ni manifeste, ni bail, ni journal).
2. Password grant → `access_token`, `expires_in`, `expires_at`, `refresh_token` (**jamais utilisé, jamais stocké**). Cohérence exigée avant toute écriture du bail : charge utile du JWT décodée en base64url (lecture des claims, **pas** de vérification de signature, **pas** de secret) ; `iss` = `https://<ref>.supabase.co/auth/v1`, `sub` = uid créé, `exp` (claim) = `expires_at` (réponse) à ±5 s et ≈ `now + expires_in`, `aud` = `authenticated`, `role` = `authenticated`. Toute incohérence ⇒ `fail`, compte nettoyé, aucun bail.
3. Preuve « valide avant échéance » **sans mutation** : `POST <function-url>` avec `Authorization: Bearer <token>`, `apikey` publishable, **sans corps multipart**. Attendu : **422** avec l’enveloppe de la fonction `{"error":"…"}` (« contenu envoyé invalide » / « choisissez un fichier »), qui prouve que la plateforme (`verify_jwt`) **et** `getUser` de la fonction ont accepté le jeton ; un 401 ⇒ `fail` (jeton non accepté) ; 2xx ⇒ `fail` (mutation inattendue) ; vérification de fuite sur le corps. Aucune écriture : aucun `documents`, aucun objet Storage (relecture à zéro sous le préfixe `<uid>/`).
4. Bail `lease.json` (0600, dans `--out`, hors Git) : `{version:1, suite:"expiry", runId, project, userId, email, token, issuer, tokenExpiresAt (epoch s), claimExp, grantExpiresIn, preparedAt, verifyNotBefore = exp + 60 s, leaseEndsAt = min(exp + 2 h, preparedAt + 2 h), manifestPath}`. Le **jeton** est le seul secret du bail ; le fichier est caviardé nulle part ailleurs (jamais dans `summary.md`, `result.json`, `run.log` : caviardage existant + ajout du jeton à la liste des secrets).
4 bis. **Bail inexécutable ⇒ refus et nettoyage** : si `verifyNotBefore ≥ leaseEndsAt` (TTL du projet plus long que le bail de 2 h, ou horloge incohérente), `prepare` **n’écrit aucun bail**, supprime immédiatement le compte (relecture 404), verdict `fail` « bail inexécutable : TTL %s s > fenêtre de bail » — jamais de compte laissé sans verify possible.
4 ter. **Données de cohérence dans le manifeste** (réécrit avant le bail) : `expiry: { userId, email, issuer, claimExp, tokenSha256 }` (empreinte SHA-256 hexadécimale du jeton, jamais le jeton). Le manifeste reste sans secret.
5. Verdict **`prepared`** (code de sortie 0) : `summary.md` annonce « PREPARED — expiration non encore prouvée ; relancer `--suite expiry-verify --lease <chemin>` après `verifyNotBefore` (ISO) et avant `leaseEndsAt` ». **Jamais PASS**. Le compte est laissé **intentionnellement** jusqu’au `verify` (au plus `leaseEndsAt`, ≤ 2 h). Le manifeste et le bail sont les artefacts actionnables si le `verify` n’a pas lieu.
5 bis. **Préalables (EXPIRY-REVIEW-003)** : si une étape préalable (santé Auth, pré-vol OPTIONS, sonde anonyme) échoue, `prepare` **s’interrompt avant toute création** (aucun compte semé, aucun bail) ; `prepared` n’est jamais rendu si une étape a échoué (nettoyage sauté **seulement** si le verdict est `prepared` ET aucune étape en échec).
6. Erreur/interruption pendant `prepare` (après création du compte) : nettoyage sûr immédiat (découverte + suppression UID + relecture 404) ; si le nettoyage échoue, manifeste conservé et `fail` avec message de relance. Aucun compte permanent.

### 1.4 Mode `verify`
1. Lit `lease.json` ; refus (code 2, rien écrit, rien supprimé, compte conservé) si `now < verifyNotBefore` (« trop tôt : relancer après <ISO> ») ou si projet/URL incohérents avec le bail. Si `now > leaseEndsAt` : **non-preuve** — nettoyage de l’UID, verdict `fail` « bail expiré, expiration non prouvée » (jamais PASS).
1 bis. **Cohérence bail ↔ manifeste avant tout appel** : `verify` relit le manifeste désigné par le bail (`manifestPath`, même projet, `suite: "expiry"`), recalcule `sha256(token du bail)` et exige l’égalité avec `expiry.tokenSha256`, puis relit les claims du jeton (base64url, sans secret) et exige `iss` = `expiry.issuer` = `https://<ref>.supabase.co/auth/v1`, `sub` = `expiry.userId` = `lease.userId`, `exp` = `expiry.claimExp` = `lease.claimExp`, `aud`/`role` = `authenticated`. Toute divergence ⇒ `fail` (bail altéré ou étranger), nettoyage de l’UID du **manifeste**, aucun appel Edge.
1 ter. **Preuve de cohorte Auth AVANT toute permission de nettoyage** (revue pilote de d9f94f9) : `verify` n’enregistre **jamais** l’UID du bail dans le manifeste ni ne le soumet au nettoyage avant une preuve **indépendante** : `GET /auth/v1/admin/users/<uid exact>` doit répondre 200 avec `id` = uid **et** un e-mail qui (i) respecte le motif `qa-gw-exp-<run>@qa.invalid` du run du bail, (ii) est égal à l’e-mail du bail, (iii) est égal à l’e-mail du manifeste ; le `runId` et le projet du manifeste doivent être ceux du bail et du run courant. Seulement alors l’UID est enregistré pour suppression. **Tout écart** — bail hors fenêtre, manifeste illisible, divergence uid/empreinte/claims/e-mail, e-mail hors motif, compte introuvable — ⇒ verdict **`refused`** : **aucune suppression**, aucune écriture d’un UID non validé dans un manifeste, diagnostic caviardé dans le rapport, code de sortie 1 ; le chemin de secours reste `--cleanup-manifest <manifeste écrit par prepare>` (dont les UID ont été enregistrés par prepare lui-même, avant toute authentification). Un bail altéré ne peut donc jamais faire supprimer un compte hors cohorte.
1 quater. `consumedAt` est écrit sur le **fichier de bail original** passé par `--lease` (et sur la copie `<out>/lease.json`), 0600, jeton inchangé.
1 quinquies. **Ordre d’enregistrement (EXPIRY-REVIEW-002)** : une fois — et seulement une fois — la preuve de cohorte établie, l’UID validé est **enregistré durablement dans le manifeste de la phase verify avant tout appel réseau suivant** (sonde Edge, écriture du bail) ; toute exception après cet enregistrement atteint le nettoyage (`finally`) avec l’UID présent, ou laisse un manifeste actionnable. Aucun UID non validé n’est jamais enregistré.
1 sexies. **Bornes revalidées en code** (jamais de confiance au fichier) : `parseLease` exige `verifyNotBefore = exp + 60 s`, `leaseEndsAt = min(exp, preparedAt) + 2 h`, fenêtre `≤ 2 h`, `expires_at = exp (±5 s)`, `exp > preparedAt`, e-mail du motif de cohorte du run, `issuer = https://<ref>.supabase.co/auth/v1` ; verify confronte `leaseEndsAt` au manifeste ; bail hors fenêtre ⇒ refus sans suppression.
1 septies. **Sûreté des chemins** : le bail (`--lease`) et le manifeste sont lus et écrits **uniquement** comme fichiers réguliers privés : `lstat` → lien symbolique refusé, fichier `0600` (aucun bit groupe/autres), dossier `0700` non symbolique ; refus (code 2) avant toute écriture distante ; les sorties du harnais restent 0700/0600.
2. **Compte actif, ni banni ni effacé, avant l’appel** : `GET /auth/v1/admin/users/<uid>` (clé serveur) doit répondre **200** avec `id` = uid, `email` = e-mail du bail, `deleted_at` absent/`null`, `banned_until` absent/`null`/passé ; 404, bannissement actif ou e-mail différent ⇒ **non-preuve** (`fail`), nettoyage, aucun appel (un 401 sur un compte banni/effacé ne prouverait pas l’expiration).
3. Appel **réel** de la fonction déployée avec le **même** jeton (lu du bail, inchangé) : `POST <function-url>` sans corps, `Authorization: Bearer <token expiré>`, `apikey` publishable. Exigé : **401** et aucune fuite (JWT, chemin, code SQL, clé). Verdicts selon le corps :
   - enveloppe de la fonction `{"error":…}` (refus par `getUser` de la fonction) ⇒ `pass` ;
   - enveloppe plateforme `{"code":"<chaîne>","message":"<non vide>"}` dont le `code` est **dans la liste liée** `EXPIRED_PLATFORM_CODES` ⇒ `pass` ; cette liste est **vide tant que le code réel d’un JWT expiré n’a pas été observé** ;
   - enveloppe plateforme avec un `code` chaîne `UNAUTHORIZED_*` **inconnu** ⇒ verdict **`observed`** (code 0) : le code est enregistré dans le rapport (`observedCode`), le nettoyage doit être propre, **ce n’est pas un PASS** ; le pilote lie ensuite ce code strictement dans un commit de suivi (même méthode que ac72c38), après quoi seul ce code donne `pass` ;
   - **exclus explicitement** (⇒ `fail`, car ils prouveraient un défaut de transport ou d’en-tête, pas l’expiration) : `UNAUTHORIZED_NO_AUTH_HEADER`, `UNAUTHORIZED_INVALID_JWT_FORMAT`, tout corps sans `code` chaîne (`{"message":…}` seul, `code` numérique), corps vide/générique/tableau, `code` ne commençant pas par `UNAUTHORIZED_` ;
   - 422 (jeton encore accepté), 2xx, 5xx, autre 4xx ⇒ `fail`.
4. Contrôle de cohérence temporelle : `now ≥ claimExp + 60 s` au moment de l’appel (horloge locale) **et** le 401 n’est pas celui d’un en-tête absent (`UNAUTHORIZED_NO_AUTH_HEADER` ⇒ `fail`, car il prouverait un défaut de transport, pas l’expiration).
5. Nettoyage : suppression Auth admin de l’UID, relecture **404** ; découverte de cohorte (lignes `documents`/objets sous `<uid>/` : attendus à zéro) ; verdict `pass` seulement si 401 sans fuite avec un corps **lié** (fonction ou code lié) **et** cohérence bail/manifeste **et** 200 actif avant **et** 404 après **et** aucune lecture inconnue ; `observed` si tout est identique sauf le code encore non lié ; `fail` sinon. Le bail est réécrit avec `consumedAt` (jeton conservé tel quel, 0600) ; le pilote supprime le dossier privé.
6. Erreur/interruption ⇒ nettoyage sûr ou manifeste actionnable (`--cleanup-manifest`), jamais d’abandon muet.

## 2. Révocation pendant un VRAI upload — protocole de concurrence (revue avant tout code)

### 2.1 Objectif
Prouver, sur la fonction déployée, qu’une révocation **validée après le pré-contrôle et avant la finalisation** d’un upload réel aboutit à un **403 avec compensation de l’objet** (GW-REV-001/002), puis relectures `documents`/objet absentes — et non seulement le refus d’un jeton déjà révoqué. Un ordre non prouvé, une issue incertaine (503) ou une fenêtre non exercée ⇒ **FAIL / non-preuve**, jamais PASS théorique.

### 2.2 Contraintes d’exécution (v4 — revues pilote 46f6cf5, root `GATEWAY_REVOKE_CONTRACT_46F6CF5.md` et blocage root sur v3 : rôles de la table de mesures)
- **Ni psql ni libpq** : le pilote exécute du SQL par `supabase db query --file` (Management API), qui envoie un **lot**. Un `begin` ne peut pas s’étendre sur deux appels CLI : verrou, pause, révocation, `commit` et relecture post-commit tiennent **dans un seul lot**. Le lot ne présume **pas** que la CLI renvoie plusieurs jeux de résultats : toutes les mesures sont accumulées dans une table temporaire de session et le lot se termine par **une seule ligne structurée** (jsonb) qui les contient toutes.
- Aucun horodatage local (retour CLI, mtime, ordre d’écriture de fichiers) n’est une heure de `commit`. Les seules horloges de preuve sont des `clock_timestamp()` **de la base**, renvoyés dans la ligne finale ; `t_after_commit` est une **borne supérieure**, pas l’instant du commit.
- `finalize_document_upload` (013) prend d’abord `lock_intervention_organization(p_intervention_id)` = `select … for update of o` sur **l’organisation** du dossier (puis `for share` sur le dossier). Le pré-contrôle (`can_access_intervention`) et l’upload Storage **ne sont pas bloqués** ; la finalisation l’est tant que le lot tient le verrou. 009 vérifie le propriétaire et sérialise sur l’organisation ; 013 verrouille cette même organisation puis relit `owns_intervention`.
- PostgREST applique `statement_timeout` au rôle `authenticated` (valeur projet, non établie par ce contrat) : **pause du lot ≤ 3 s**, `lock_timeout` 2 s, `statement_timeout` 8 s pour le lot. Ni 5 s ni 8 s de fenêtre ne sont supposés ; la pause n’est **jamais** augmentée pour « faire apparaître » la fenêtre. Si la latence/timeout rend l’observation impossible, le résultat est « fenêtre non exercée », jamais un PASS théorique.
- Tout est préparé **avant** le lot : acteurs, JWT (password grant), organisation/site/dossier, manifeste, résultats attendus. **Aucune création ni connexion** pendant la fenêtre.

### 2.3 Acteurs et données (cohorte dédiée, jamais une ligne réelle) — variante site, sans admin
Cohorte du harnais : client QA, artisan QA attribué, **propriétaire QA** (crée organisation et site QA par `create_site`), **gestionnaire QA révoqué** = **membre** `manager` de l’organisation QA — **jamais** le propriétaire, un admin, le client direct ni l’artisan attribué — à portée `selected` avec **un seul** grant `can_write` sur le site QA (posé par le propriétaire via `set_organization_member_site_access`). Dossier de **site** QA créé par le propriétaire. **Acteur de l’upload = le gestionnaire QA** (JWT réel du gestionnaire). Révocation = **vrai RPC** `set_organization_member_site_access(<org QA>, <gestionnaire QA>, 'selected', '[]'::jsonb)` exécuté **sous l’identité du propriétaire QA** (rôle `authenticated` + claims locaux `sub` = propriétaire). Aucune promotion, aucun admin fictif, aucun `UPDATE` direct des permissions. (Un upload par le propriétaire ne prouverait aucune perte de droit.)

```
begin
 if current_setting('role', true) is distinct from 'authenticated' then raise exception 'acteur RPC non prouvé : role=%', current_setting('role', true); end if;
 if auth.uid() is distinct from '<propriétaire QA>'::uuid then raise exception 'acteur RPC non prouvé : auth.uid()=%', auth.uid(); end if;
 perform set_config('qa.actor_role', current_setting('role', true), true), set_config('qa.actor_uid', auth.uid()::text, true);
end $$;
select public.set_organization_member_site_access('<org QA>', '<gestionnaire QA>', 'selected', '[]'::jsonb);
reset role;
-- Mesures reprises sous le rôle racine : preuve de l'acteur recopiée depuis les GUC, t_revoked = borne supérieure
-- de la fin du RPC ; rpc_ok n'existe que si le RPC a retourné (sinon le lot est déjà avorté).
insert into qa_rv values('actor_role', to_jsonb(current_setting('qa.actor_role', true))), ('actor_uid', to_jsonb(current_setting('qa.actor_uid', true))),
                        ('t_revoked', to_jsonb(clock_timestamp())), ('rpc_ok', 'true');
commit;
-- Après commit : relecture autoritaire de la révocation (portée et grants du membre), puis borne supérieure.
insert into qa_rv select 'readback', jsonb_build_object('scope', (select scope from public.organization_member_site_scopes where organization_id='<org QA>' and user_id='<gestionnaire QA>'), 'grants', (select count(*) from public.organization_member_site_grants where organization_id='<org QA>' and user_id='<gestionnaire QA>'));
insert into qa_rv values('t_after_commit', to_jsonb(clock_timestamp()));
select jsonb_object_agg(k, v) as result from qa_rv;   -- LA ligne finale unique
```
**Rôles et table de mesures (v4, blocage root sur v3)** : `qa_rv` est créée par le rôle racine ; sous `set local role authenticated`, un `insert` dans cette table serait refusé (`permission denied`) et ferait avorter tout le lot. Option retenue : **aucun GRANT** — toutes les écritures de mesures (`t_begin`, `batch_pid`, `t_lock`, `t_before_revoke`, `t_revoked`, `rpc_ok`, `readback`, `t_after_commit`) et les `set_config` des claims sont exécutés **sous le rôle racine**, et la section `set local role authenticated … reset role` ne contient **que** l’appel du RPC (l’acteur du RPC reste le propriétaire QA via les claims locales, posées avant le changement de rôle et valables pour la transaction). Pourquoi cela n’élargit rien : aucun privilège n’est accordé à `authenticated` (ni sur `qa_rv`, ni ailleurs) ; `qa_rv` est une table **temporaire** de session, propriété du rôle racine, détruite à la fin de la session et vide après rollback ; aucun objet persistant n’est créé ; la ligne finale unique est inchangée. Conséquence sur les mesures : `t_before_revoke` précède le `set local role` (écart négligeable) et `t_revoked` suit le `reset role` : c’est une **borne supérieure** de la fin du RPC, ce qui reste suffisant pour `t_observed ≤ t_before_revoke ≤ t_revoked < t_after_commit`.

**Preuve de l’acteur du RPC (revue root complète de v3)** : `current_user` à l’intérieur d’une fonction `security definer` n’est pas une preuve. Le lot, **après** `set local role authenticated` + claims et **avant** le RPC, exécute un bloc `do` sous `authenticated` qui **vérifie** `current_setting('role') = 'authenticated'` et `auth.uid() = <propriétaire QA>` et **lève** (lot avorté, aucune révocation tentée) sur tout écart ; les deux valeurs sont **enregistrées** dans la ligne finale (`actor_role`, `actor_uid`) via des GUC locales à la transaction (`qa.actor_role`, `qa.actor_uid`, posées par `set_config(…, true)` sous `authenticated`, lues par le rôle racine après `reset role`) — aucun GRANT, aucun objet persistant ; le bloc `do` (plpgsql, langage de confiance) et `auth.uid()` sont déjà exécutables par `authenticated`.

Si la garde, `lock_timeout`, `statement_timeout` ou le RPC lève, la transaction est annulée (`rollback` implicite) : **non-preuve** ; aucune nouvelle mutation n’est envoyée après un arrêt ; la fermeture du processus CLI ne signifie pas que la transaction est terminée. Une seule exécution par run ; la **source exacte** (UUID substitués, garde complète) est relue par root avant toute tentative.

### 2.5 L’observation unique (lecture seule, second appel CLI pendant la pause)
Une **seule** requête relie, à la même `clock_timestamp()` de la base, (a) la finalisation bloquée et (b) l’objet Storage exact :
```
select clock_timestamp() as t_observed, a.pid as finalize_pid, a.wait_event_type, a.wait_event, pg_blocking_pids(a.pid) as blocked_by,
       exists(select 1 from storage.objects o where o.bucket_id='intervention-documents' and o.name='<gestionnaire QA>/<uuid objet>') as object_visible
from pg_stat_activity a where a.query ilike '%finalize_document_upload%' and a.pid <> pg_backend_pid();
```
Attendu : **exactement une** ligne, `wait_event_type = 'Lock'`, `blocked_by` contenant **directement** `batch_pid`, `object_visible = true`, `t_lock ≤ t_observed ≤ t_before_revoke`.

**Découverte bornée ≠ preuve (décision root sur 13b68c3)** : le nom de l’objet est un UUID choisi par le serveur et n’existe qu’après l’upload ; le préfixe `<gestionnaire QA>/` (bucket `intervention-documents`) sert **uniquement** à borner la **découverte** à l’UID de la cohorte. La **preuve** est l’observation SQL unique, qui renvoie `object_count` (nombre d’objets sous ce préfixe) et `object_name` (le nom exact, renseigné seulement si `object_count = 1`) à `t_observed` ; le harnais exige `object_count = 1`, `object_name` = **exactement** le chemin qu’il a lui-même découvert, ce chemin sous l’UID du gestionnaire (`<uid>/<UUID>`) **et enregistré dans son manifeste** (le même chemin est relu absent après le 403). `object_count` 0 ou ≥ 2, nom différent, chemin non rattaché au manifeste ou hors UID ⇒ **non-preuve (FAIL)** ; un préfixe arbitraire n’est jamais une preuve. Le parseur rejette aussi une ligne incohérente (`object_count = 1` sans nom, nom renseigné avec `object_count ≠ 1`, champ absent).
