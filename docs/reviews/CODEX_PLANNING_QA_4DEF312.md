## 2. Constats

### P2-1 — Navigateur : le formulaire d'entrée ponctuelle n'est rendu qu'après « Ajouter une entrée ponctuelle » (fausse FAIL)
`scenarios.mjs:112` localise `form` contenant le titre « Nouvelle entrée ponctuelle » sans ouvrir le formulaire. Dans la feuille `b26bc45` `components/features/planning/artisan-planning.tsx:272`, `EntryForm` rend **seulement** un bouton « Ajouter une entrée ponctuelle » tant que `open` est faux ; le `<form>` et son `<h3>` n'existent pas dans le DOM. Sur une UI correctement raccordée, l'étape « browser: actual planning form commits exactly one private entry » échouera en dépassement (FAIL), à tort. Corollaire `:129` : `count(heading 'Nouvelle entrée ponctuelle') === 0` pour l'artisan suspendu est **vide de preuve** (vrai aussi pour un artisan autorisé, formulaire fermé). Correction attendue : cliquer `getByRole('button', { name: 'Ajouter une entrée ponctuelle', exact: true })` avant de remplir ; pour la suspension, asserter l'absence de ce bouton **et** la présence de la note `role="note"` (`artisan-planning.tsx:61`).

### P2-2 — SIGINT pendant la suite navigateur : Playwright sort en 130 avant le nettoyage à la base `c92f4de`
`run.mjs:75,77` traite SIGINT/SIGTERM en levant la porte (`gate.stop()`) et en marquant `interrupted`, puis laisse le flux normal atteindre `finally → finish()`. Pour la suite API c'est correct (prochaine mutation refusée → FAIL → nettoyage, code 1). Pour la suite navigateur, à `c92f4de` `launchBrowser` n'opte pas hors des gestionnaires de signaux de Playwright : sur Ctrl-C, Playwright tue le navigateur et appelle `process.exit(130)` **avant** `finish()` — cohorte conservée, nettoyage par `--cleanup-manifest` seulement. Mon `dc7209d` (intégré dans `c0fc095`) passe `handleSIGINT/SIGTERM/SIGHUP: false` dans `launchBrowser` ; le harnais Codex en bénéficie dès que le checkout servi/intégré contient ce commit. À défaut, Codex doit passer ces options lui-même. Noter aussi : aucun second signal n'abandonne un nettoyage bloqué (seul SIGKILL), et une étape en attente longue (navigateur, `timeout` jusqu'à 120 s) retarde le nettoyage d'autant.

### P2-3 — Couverture : la preuve de concurrence exigée par `b26bc45` sur les rendez-vous n'est pas apportée
`CLAUDE_ADV_PLANNING_CONTRACT.md` l.257 (« Ce que Codex doit vérifier ») demande : deux connexions, même artisan, `save_intervention_appointment` **et** `save_planning_entry(busy)` chevauchants → une réussite, l'autre `P0001` ; idem deux `save_intervention_appointment` sur deux dossiers ; et l.258 la valeur de `current_setting('role')` dans le trigger 016 lors d'un RPC utilisateur. Le harnais ne crée aucun rendez-vous : seules les courses `busy`↔`busy` (`scenarios.mjs:26-34`) et préférences (`:44-50`) sont exercées. Le trigger `before insert/update on intervention_appointments` (garde anti-chevauchement) reste non prouvé en direct. À ajouter, ou à déclarer dans `non_proofs` et dans le rapport comme critère **non exercé** (actuellement absent des non-preuves).

### P2-4 — Couverture HTTP de la suite API limitée à l'anonyme 401
Côté `--suite api`, la seule requête HTTP Next est `GET /api/planning` anonyme → 401 (`run.mjs:90`) ; tout le reste passe par PostgREST/RPC. Les points « Recette HTTP » de `b26bc45` l.259 (non-artisan → 403, tiers sur `/api/planning/slots` → 403, curseur d'un autre filtre → 422, marquage d'un identifiant d'autrui, préférences version périmée → 409) ne sont couverts qu'en partie et seulement dans la suite navigateur (`GET /api/planning` 200/403, `POST` 422/403). Le contrat Codex l'annonce (« par HTTP via navigateur si disponible »), mais comme le pilote exécute l'API d'abord, ces critères HTTP ne seront pas prouvés à ce stade ; le rapport doit le dire explicitement.

### P2-5 — Reprise après résultat incertain : aucune voie outillée pour lever les marqueurs
`cleanup()` refuse toute suppression tant que `manifest.uncertain` ou une intention non `done` existe (`core.mjs:103`), y compris en mode `--cleanup-manifest` (`validateManifest` conserve les marqueurs). C'est le bon réflexe fail-closed, mais la seule issue est l'édition manuelle d'un JSON 0600 par le pilote, sans procédure décrite (quels champs, comment consigner la réconciliation). Proposer un mode explicite (`--reconciled <id>` ou un fichier de réconciliation signé par l'opérateur) ou, a minima, documenter la procédure dans `CODEX_PLANNING_QA.md`.

### P3-1 — Préflight : la raison du refus est avalée
`run.mjs:19` : `catch {}` imprime un message générique ; le pilote ne sait pas lequel des contrôles (0600, projet, URL, SHA, sortie dans Git, Playwright) a échoué. Imprimer `error.message` redacté.

### P3-2 — Granularité : première étape en échec = arrêt de toute la suite, nom d'étape erroné après SIGINT
`run.mjs:88-96` : un seul `try/catch` autour de toutes les étapes ; après le premier FAIL, les étapes suivantes ne sont ni exécutées ni consignées. Après SIGINT entre deux étapes, `step()` lève à `gate.check()` **avant** de poser `activeStep` (`:78`) : le FAIL est enregistré sous le nom de l'étape précédente (déjà PASS). Consigner les étapes non exécutées (`SKIPPED`) et passer le nom de l'étape en échec.

### P3-3 — `--suite browser` seul : l'étape de révocation est ignorée silencieusement
`scenarios.mjs:138` : `if (ctx.support)` — sans la suite API, l'étape « notification HTTP list/count/mark obey linked-ticket revocation » n'apparaît pas dans `result.json`. Le contrat le dit ; `result.json` devrait porter une entrée `SKIPPED` avec la raison. Note : la localisation `article` nom exact « Réponse personnelle QA » (`:147`) suppose que la suite API a déjà marqué cette notification lue (sinon le nom accessible est « …, non lue », `notification-center.tsx:125`) — cohérent uniquement en `--suite all`.

### P3-4 — Les jetons (password grant) sont traités comme des mutations à réconcilier
`run.mjs:86` : `token()` passe par `change(...)` ; un échec de transport marque l'intention `uncertain` et **bloque le nettoyage** alors qu'une session n'a rien à réconcilier. Fail-closed, donc sans risque, mais source de reprises manuelles inutiles. Utiliser `request()` directement (hors `mutate`).

### P3-5 — Codes de sortie : SIGINT → 1 ici, 130 dans `scripts/qa`
Convention déclarée par le contrat Codex (« interruption jamais transformée en succès »), compatible, mais différente de `scripts/qa/run.mjs` (130 après nettoyage, `dc7209d`). À signaler au pilote pour l'interprétation des codes.

### P3-6 — Revendication de test « finalisation unique / signal »
`CODEX_PLANNING_QA.md:58` annonce des tests « stop/drain et finalisation unique/signal ». Les tests couvrent `Gate`, `mutate`, `cleanup`, `finalCode` ; les gestionnaires `interrupt`/`fatal` et `finish()` sont inline dans `run.mjs` et **ne sont pas testés** (non extraits dans `core.mjs`). Reformuler, ou extraire `finish`/`interrupt` dans `core.mjs` avec un test à faux processus (modèle : `scripts/qa/tests/lifecycle.test.mjs`).

### P3-7 — Journal console non recopié
`record()` écrit `STATUS: name` sur stdout ; aucune copie redactée dans `--out` (contrairement à `run.log` du harnais de base). Les messages d'erreur ne vont que dans `result.json`/`summary.md` (redactés) — acceptable, mais une sortie console non redirigée par le pilote est perdue.
