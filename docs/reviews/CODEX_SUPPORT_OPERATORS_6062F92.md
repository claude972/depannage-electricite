## 5. Constats

Aucun P1.

- **P2-1 — Preuve de concurrence réelle absente (déclarée).** Le verrouillage `FOR SHARE` des grants puis la relecture après les verrous organisation→dossier→ticket sont corrects par lecture, mais aucune recette à deux connexions (révocation `FOR UPDATE` vs `reply`/`set_status`, CAS concurrents) n'est fournie ; le contrat §4 la réserve à root. À exécuter avant de considérer la garantie « aucune écriture après révocation commitée » comme prouvée. Référence : `018:47-61,72-78`, contrat l.43.
- **P2-2 — Démotion concurrente d'un super admin hors garantie.** `lock_support_operator_permissions` retourne `true` pour `is_admin()` sans verrou de profil (`018:52`, commentaire l.46) ; une démotion simultanée pourrait laisser aboutir une écriture « admin » ; le contrat l'annonce explicitement (« n'est pas une nouvelle garantie », chemin admin 011 préservé). À conserver dans les non-preuves du pilote.
- **P3-1 — Second filet de relecture plus faible que le verrou.** Après les verrous, la relecture (`018:76-78`) utilise `has_platform_scope` sans recompter les lignes `FOR SHARE` ; sûr parce que les verrous partagés sont tenus jusqu'au commit, mais une version future qui relâcherait le `FOR SHARE` (sous-transaction) perdrait la garantie ; un commentaire l'expliciterait.
- **P3-2 — Opérateur créateur de son propre ticket résolu.** Avec read+reply, la réponse sur son propre ticket résolu est refusée (`018:87`, « Explicitly reopen before replying ») et `can_reply=false` côté HTTP (`permissions.ts:19`) — cohérent avec le contrat (l.17) mais différent de l'expérience créateur (auto-réouverture) : à documenter côté UI (bouton « Rouvrir » explicite).
- **P3-3 — Migration non idempotente.** `create function` (et non `create or replace`) pour `support_operator_permissions`, `lock_support_operator_permissions`, `notify_support_status_event` : une double application échoue proprement (pas de corruption) ; conforme à la pratique des migrations précédentes.
- **P3-4 — Défaut de portée par `profiles.role`.** Le défaut `scope=all` pour un admin reste dérivé de `profiles.role` (`route.ts:26`) ; l'autorisation, elle, vient de la RPC. Acceptable (contrat « défaut conservé all pour admin ») ; un opérateur non-admin doit demander `scope=all` explicitement, ce que l'UI opérateur doit faire.
