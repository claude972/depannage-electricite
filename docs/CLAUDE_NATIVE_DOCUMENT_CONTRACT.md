## Pourquoi une requête multipart unique et non un upload direct signé

Le Web lit les octets côté serveur et vérifie les magic bytes avant toute écriture. Une URL d’upload signée laisserait le client écrire directement dans Storage sans ce contrôle de contenu, et la métadonnée MIME Storage reposerait sur la déclaration du client. Le fichier plafonné à 4 MiB tient dans la mémoire d’une fonction (256 Mo). Le gateway reçoit donc le fichier, le valide, l’écrit puis finalise. Pas d’upload reprenable (resumable), pas de deuxième étape signée.

## Module partagé `document-policy`

Exports : `DOCUMENT_BUCKET = "intervention-documents"`, `MAX_DOCUMENT_BYTES = 4194304`, `MAX_REQUEST_BYTES = 4400000` (plafond Content-Length, marge multipart), `ALLOWED_DOCUMENT_MIME` (image/jpeg, image/png, image/webp, application/pdf), `DOCUMENT_NAME_MAX = 160`, `detectType(bytes: Uint8Array): AllowedMime | null` (JPEG FF D8 FF ; PNG 89 "PNG" ; PDF "%PDF-" ; WebP "RIFF"…"WEBP"), `validateDocumentUpload({ size, declaredType, bytes })` → `{ ok: true, mime }` ou `{ ok: false, reason: "empty" | "too_large" | "type_mismatch" }`, `documentNameFor(name)` (tronque à 160, remplace un nom vide par « document »), `isAllowedMime(value)`.

Validation identique au Web : taille 1..4 194 304 octets ; type détecté par les octets ; le MIME déclaré par le client doit être exactement égal au type détecté ; tout autre contenu refusé. Le module ne fait pas confiance au MIME déclaré ni à l’extension du nom.

## Contrat HTTP de `POST /functions/v1/native-document-upload`

En-têtes : `Authorization: Bearer <access_token utilisateur>` (jeton de session Supabase du natif), `apikey: <clé publishable>` (exigée par la plateforme). Aucune session cookie, aucun jeton de bypass Vercel, aucune clé secrète côté client.

Corps `multipart/form-data` : `file` (obligatoire, un seul fichier), `intervention_id` (UUID optionnel). Aucun autre champ accepté comme preuve d’identité ou de droit : propriétaire, chemin, MIME et date sont produits côté serveur.

Réponse `201` : `{ "document": { "id", "name", "mime_type", "created_at" } }` (mêmes champs que le Web). Toutes les réponses portent `Cache-Control: private, no-store`. Pré-vol `OPTIONS` répondu 204 pour une éventuelle cible web Expo ; aucun cookie/credential n’est admis par CORS.

Erreurs `{ "error": "<message français>" }` :
- `401` : en-tête absent, jeton invalide/expiré/révoqué (`auth.getUser` refuse), ou utilisateur introuvable.
- `403` : dossier non lisible ou inexistant (une seule réponse, pas d’oracle d’existence) ; rôle en lecture seule (membre viewer, membre site sans `can_write`, artisan non affecté) ; droits révoqués détectés au pré-contrôle ou à la finalisation.
- `404` : l’objet Storage attendu au chemin propriétaire n’existe pas au moment de la finalisation (défaillance interne ou suppression concurrente). L’objet éventuellement créé par la tentative est compensé.
- `405` : méthode autre que POST/OPTIONS.
- `409` : identifiant/chemin déjà utilisé ou règle métier P0001 ; aucun document accessible créé.
- `413` : `Content-Length` > 4 400 000 ou fichier > 4 194 304 octets.
- `415` : MIME déclaré hors liste, ou contenu dont les magic bytes ne correspondent pas au MIME déclaré (le Web renvoie 422 pour ce cas ; la validation est identique, seul le code transport diffère et est documenté ici).
- `422` : `file` absent/vide, `intervention_id` non UUID, nom invalide.
- `429` : quota `check_upload_limit` (10 uploads/minute/compte, inchangé) atteint — code SQL 53300.
- `503` : configuration serveur absente, Storage ou base indisponible.
- `500` : exception inattendue du handler (message générique). Aucune donnée interne, aucun code SQL brut, aucun chemin Storage n’est renvoyé par aucune réponse.

Pas d’idempotence par nom de fichier ou date : chaque tentative choisit un UUID neuf et un chemin neuf. Une réponse perdue côté client ne peut pas être « rejouée » ; le client relit la liste des documents du dossier (RLS) pour constater l’état. Aucune idempotence par hash de contenu n’est retenue dans ce lot.

## Déroulé serveur et compensation

1. `OPTIONS` → 204 ; méthode ≠ POST → 405. Extraction du Bearer ; absence → 401.
2. Client supabase-js « utilisateur » : `createClient(SUPABASE_URL, clé publishable/anon, { global: { headers: { Authorization } }, auth: { persistSession: false, autoRefreshToken: false } })` puis `auth.getUser(token)`. Erreur ou utilisateur nul → 401. Rien n’est lu dans le corps pour identifier l’utilisateur.
3. `Content-Length` > 4 400 000 → 413 avant lecture du corps. `formData()` ; `file` non File → 422 ; `intervention_id` présent mais non UUID → 422.
4. Pré-contrôle identique au Web, sous RLS de l’utilisateur : `select id, artisan_id from interventions where id = …` (non visible → 403) ; `rpc owns_intervention`, `rpc is_admin` ; refus 403 si ni propriétaire/gestionnaire site, ni admin, ni artisan affecté. Document personnel (sans `intervention_id`) : tout utilisateur authentifié, comme le Web (parcours pièces artisan préservé).
5. `rpc check_upload_limit` (53300 → 429) avant toute écriture.
6. Lecture des octets ; `validateDocumentUpload` : `empty` → 422, `too_large` → 413, `type_mismatch` → 415.
7. `id = crypto.randomUUID()`, `path = <uid>/<id>`. Upload Storage via le client serveur de la fonction (`upsert: false`, `contentType` = type détecté). Erreur → 503 et compensation best-effort du chemin de cette tentative (il peut avoir été écrit malgré une erreur réseau ; personne d’autre ne peut l’avoir créé).
8. `rpc finalize_document_upload(p_id, p_path, p_name, p_mime, p_intervention_id)` **avec le client utilisateur** (auth.uid() réel, pas la clé serveur). Un 201 n’est renvoyé que si la ligne retournée est **exactement** celle demandée (revue GW-REV-002) : `id` = UUID choisi, `path` = `<uid>/<id>`, `owner_id` = utilisateur vérifié, `name`/`mime_type`/`intervention_id` tels qu’envoyés, `created_at` chaîne non vide. Toute autre valeur (`null` sans erreur, `{}`, `[]`, autre id/chemin/propriétaire, champ manquant) est traitée comme une issue **incertaine** : 503 incertain, objet conservé, aucune compensation (la base a pu valider quelque chose), journal opérateur limité à l’identifiant de tentative (jamais de chemin, d’utilisateur ni de nom).
9. Échec de finalisation. Règle (revue GW-REV-001) : la suppression de l’objet n’est décidée **que** par une erreur définitive renvoyée par la base — un code SQL levé **dans** la fonction (42501, P0001, P0002, 53300, 22xxx, 23xxx), qui prouve le rollback. Toute incertitude de transport (fetch jeté, délai dépassé, pas de réponse HTTP, 5xx sans code PostgreSQL, code PGRST…) laisse la transaction possiblement en vol : elle peut encore être validée après coup. Dans ce cas l’objet est **conservé** et la réponse est explicitement incertaine. La relecture de `documents` par `id` (client serveur, erreur propagée par `index.ts`) sert **uniquement** à renvoyer 201 quand la ligne existe déjà ; une relecture « aucune ligne » ou en erreur ne décide jamais d’une suppression. Table des issues :

| Finalisation | Relecture | Objet Storage | Réponse |
|---|---|---|---|
| succès | — | conservé | 201 |
| toute erreur/exception, ligne trouvée **et conforme** | trouvée | conservé | 201 (réponse perdue après commit) |
| succès ou relecture avec ligne **non conforme** (`{}`, `[]`, autre id/chemin/propriétaire, champ manquant) | — | **conservé** | 503 incertain (journal : id de tentative seulement) |
| code SQL définitif (42501, P0002, 23505, 22xxx, 53300…) | aucune ligne ou relecture en erreur | **supprimé** (ce chemin seul) | 403 / 404 / 409 / 422 / 429 selon le code |
| incertitude de transport (exception, code absent ou non-SQL : PGRST, 57014, 08006…) | aucune ligne ou relecture en erreur | **conservé** | 503 `{ error: "L’enregistrement du fichier est incertain. Vérifiez la liste des documents du dossier avant de réessayer.", uncertain: true }` |

Dans le cas incertain, le gateway n’affirme jamais l’échec et ne supprime rien : une ligne `documents` a peut-être été, ou sera, validée et référence l’objet. Le client relit la liste des documents (RLS) après un court délai ; s’il ne trouve rien, il recommence avec un nouveau fichier/identifiant. Un objet non référencé reste illisible (policies inchangées) ; son nettoyage relève d’une tâche opérateur ultérieure, hors de ce lot. Aucune suppression par préfixe, par propriétaire ou par nom ; jamais un objet d’une autre tentative.

## Migration 013 — `finalize_document_upload`

Additive uniquement. Aucune policy créée/modifiée, aucun `create or replace` de `is_admin`, `owns_intervention`, `can_access_intervention`, `can_access_site`, `can_manage_site`, aucune modification de `documents`, du bucket ou des grants existants.

```
create function public.finalize_document_upload(p_id uuid, p_path text, p_name text, p_mime text, p_intervention_id uuid default null)
returns public.documents language plpgsql security definer set search_path=''
```
Ordre des contrôles et des verrous :
1. `auth.uid()` nul → `insufficient_privilege` (42501). Aucun paramètre ne désigne l’utilisateur.
2. `p_path` doit valoir exactement `auth.uid()::text || '/' || p_id::text` sinon 42501 : un utilisateur ne peut jamais finaliser un objet hors de son dossier propriétaire ni réclamer un objet d’autrui.
3. `p_name` 1..160 caractères et `p_mime` dans la liste autorisée sinon `invalid_parameter_value` (22023).
4. Si `p_intervention_id` non nul : `lock_intervention_organization(p_intervention_id)` (verrou organisation du site, ordre établi par 009/012), puis `select … from interventions where id = … for share` (sérialise avec `reassign_intervention`, `intervention_action` et les changements de portée/membres qui verrouillent l’organisation `for update`, sans bloquer d’autres uploads concurrents sur le même dossier). Dossier absent → 42501 (pas d’oracle). Puis `coalesce(owns_intervention(p_intervention_id) or is_admin() or job.artisan_id = auth.uid(), false)` sinon 42501. Un retrait de membre, une réduction de portée site ou une réaffectation artisan commis avant ce point est observé : aucune métadonnée n’est créée et l’objet est compensé par le handler.
5. Existence réelle de l’objet : `exists(select 1 from storage.objects where bucket_id = 'intervention-documents' and name = p_path)` sinon `no_data_found` (P0002). Impossible de référencer un objet non écrit ou déjà supprimé.
6. `insert into public.documents(id, intervention_id, owner_id, name, path, mime_type)` avec `owner_id = auth.uid()` ; `returning *`. `documents.path` unique et `id` clé primaire → 23505 si réutilisation.

Grants : `revoke execute … from public, anon, authenticated` puis `grant execute … to authenticated`. La fonction n’accorde aucune lecture supplémentaire : la lisibilité reste régie par `documents_read` et `documents_objects_read` inchangées. Aucun verrou n’est pris pour un document personnel (pas de dossier). Jamais de verrou profil ou artisan ici : l’ordre organisation → dossier est le seul utilisé, compatible avec 012 (organisation → dossier → profil).

## Ce que ce lot ne change pas (limites honnêtes)

- Le Web continue d’insérer les métadonnées avec le client admin après upload ; seule la validation devient partagée. Basculer le Web sur la même RPC est une ligne à changer **après** application de 013 sur la base dédiée ; le faire avant casserait les uploads Web sur une base sans 013. Décision laissée au pilote.
- Aucune URL publique, aucun bucket public, aucun upload reprenable, aucune OCR/analyse, aucune miniature, aucune suppression de document côté natif, aucune limite supplémentaire par dossier.
- Idempotence non retenue : pas de corrélation nom/date, pas de hash de contenu dans ce lot.
- La fonction Edge n’est pas déployée par cet agent ; `verify_jwt` reste la valeur par défaut (true) ; aucun secret créé. Le natif devra appeler la fonction avec `supabase.functions.invoke` ou `fetch` + Bearer de session.
- Les tests Node utilisent de fausses dépendances et le test SQL un PostgreSQL isolé avec stubs Auth/Storage : ni l’un ni l’autre ne prouvent un interleaving réseau réel ; les scénarios de retrait concurrent sont séquentiels (retrait commis avant finalisation) et la structure des verrous est vérifiée en source.
- Le contrôle d’existence Storage porte sur `bucket_id`/`name` ; la métadonnée MIME Storage n’est pas relue (le MIME retenu vient des magic bytes lus par le serveur et de `contentType` qu’il a fixé).

### Correction GW-HARNESS-003 — découverte de cohorte avant toute suppression

Constat du pilote (revue de 7fa4e95) : un délai HTTP dépassé **après** qu’un upload a été validé côté serveur sortait de `runScenarios` avant les contrôles de fin de parcours ; le nettoyage pouvait alors supprimer les lignes `documents` du propriétaire (par `owner_id`) sans connaître le chemin de l’objet Storage, laissant un orphelin absent du manifeste. Le code du gateway (GW-REV-001/002) est inchangé ; seul le harnais est corrigé.

Règles désormais appliquées par `runCleanup` (`scripts/qa-gateway/lib.ts`, orchestration pure sur un client injecté ; `run.mjs` fournit le client `fetch`) :

1. **Découverte dans le nettoyage lui-même, avant toute suppression, sur chaque chemin de sortie** : fin normale, délai HTTP, interruption (SIGINT/SIGTERM), erreur non gérée, et relance `--cleanup-manifest`. Elle liste les lignes `documents` de la cohorte par `owner_id` (utilisateurs du manifeste) **et** par `intervention_id` (dossiers du manifeste), avec `Prefer: count=exact` + `Range` paginés et `order=id.asc`, puis les objets Storage sous chaque préfixe `<uid>/` via l’API de listage (`sortBy name`, pages de 1000, offset). Tout ce qui est trouvé (`id` et `path` des lignes, `<uid>/<nom>` des objets) est **fusionné dans le manifeste en une seule réécriture atomique avant la première suppression** ; les objets Storage sont supprimés avant les lignes `documents` qui les référencent (ordre du plan inchangé).
2. **Une lecture inconnue interdit le verdict propre** : erreur HTTP, exception/délai, absence de compte exact, page vide avant le total annoncé, pagination plafonnée (100 pages), ligne sans id UUID, chemin ou nom d’objet hors convention `<uid>/<id>`, **entrée de listage Storage sans `name` (ou de toute autre forme que `{name: string}`, `parseStorageListing`) — jamais traitée comme absente, y compris dans la relecture après suppression** → entrée `unknown` (`{scope, detail}`) conservée dans le manifeste, **aucune suppression effectuée** (ni objets, ni lignes, ni utilisateurs : supprimer une ligne sans connaître son objet recréerait l’orphelin), étape `fail` « découverte de cohorte incomplète avant nettoyage » avec le message exact à relancer (`--cleanup-manifest <out>/manifest.json`), verdict `fail`, code de sortie 1. Une relance refait la découverte ; les `unknown` de l’ancien manifeste sont informatifs et remplacés par le résultat courant.
3. **Signaux** : `SIGINT`/`SIGTERM` n’interrompent plus le processus : le premier signal annule la phase en cours (`AbortController` composé avec le délai de 30 s), le `catch` journalise « interruption » et le `finally` exécute découverte + nettoyage avec un contrôleur neuf ; un second signal annule les requêtes du nettoyage (manifeste conservé, verdict `fail`) ; un troisième sort immédiatement (130). Un crash **dans** le nettoyage est capturé : verdict `fail`, manifeste sur disque, message de relance.
4. **Réconciliation tardive après une phase interrompue** : un délai dépassé ou une annulation (signal, erreur) sur un upload/une finalisation **ne prouve pas** que le serveur n’a pas validé. Quand le `catch` « interruption » a été atteint (et en mode `--cleanup-manifest`), `runCleanup` répète la découverte avec repli exponentiel **sur toute la fenêtre, sans sortie anticipée** (`RECONCILE` : 4 passes précédées de 2 s, 4 s, 8 s, 16 s ; **fenêtre garantie avant toute suppression = 30 s de replis**, `reconcileWindowMs` = base × (2^passes − 1), plus la durée des lectures) ; une passe « rien de nouveau » ne raccourcit jamais la fenêtre, car un délai dépassé reste incertain ; chaque règlement tardif trouvé est fusionné dans le manifeste (réécriture atomique) avant la suppression ; une lecture en erreur réessaie à la passe suivante ; la suppression n’a lieu que si la **dernière passe** est complète et ne trouve rien de nouveau — sinon (dernière passe en erreur, ou règlement encore trouvé à la dernière passe) → `unknown` conservé, **aucune suppression**, verdict `fail` avec le message de relance. Après la passe de suppression, une **réconciliation finale** (a) relit la cohorte (découverte) pour détecter un règlement arrivé entre-temps et (b) vérifie la **présence actuelle de chaque élément connu du manifeste** (`verifyKnownAbsent` : lignes `documents` par `id`, paginées à compte exact, par lots de 50 ; objets Storage par chemin exact via listage `search`) ; toute réapparition d’un élément connu, toute nouveauté ou toute lecture qui ne peut confirmer l’absence → fusionné dans le manifeste, `fail` « réconciliation finale », relance `--cleanup-manifest`. Un run nominal (aucune interruption) ne dort jamais : une seule découverte, pas de réconciliation.
5. Les contrôles de fin de parcours (« aucune métadonnée créée par les tentatives refusées », « aucun objet orphelin ») réutilisent la même découverte paginée ; toute lecture inconnue y est un `fail` explicite.
6. Inchangé : `fetch` seulement, jetons réels par password grant, urgence `scheduled`, sorties 0700/0600 caviardées, refus (code 2) si projet/URL incohérents, `--dry-run` sans écriture distante.

Limites : scénarios séquentiels (pas de preuve d’interleaving) ; l’affectation artisan et l’adhésion viewer sont semées par la clé serveur ; la découverte couvre les objets sous les préfixes `<uid>/` des utilisateurs du manifeste et les lignes par `owner_id`/`intervention_id` — un objet écrit hors de ces préfixes (impossible par le gateway, qui n’écrit que `<uid>/<id>`) ne serait pas vu ; un signal reçu **avant** la première écriture du manifeste ne laisse rien à nettoyer, un `kill -9` ne peut être intercepté (relancer `--cleanup-manifest`) ; la fenêtre de réconciliation est bornée (30 s de replis garantis avant suppression, puis une réconciliation finale) : un règlement plus tardif que la réconciliation finale n’est vu que par une relance `--cleanup-manifest` (qui réconcilie à nouveau) ; la réconciliation finale vérifie l’absence des éléments **connus du manifeste** et la nouveauté sous les préfixes/identifiants de la cohorte, pas davantage. **Non prouvé par cet agent** : le harnais n’a jamais été exécuté contre un projet réel (aucun identifiant ni déploiement disponible) — en particulier la forme exacte des réponses `Content-Range` de PostgREST en `HEAD`/`Range`, l’ordre stable et la pagination de l’API de listage Storage (`sortBy`, `offset`), l’annulation effective d’un `fetch` multipart par `AbortSignal.any`, la forme réelle des entrées renvoyées par le listage Storage (présence systématique de `name`, entrées de dossier) et le délai réel de règlement d’un upload interrompu (la fenêtre de 30 s est garantie côté harnais mais son adéquation au délai de règlement réel est une hypothèse) restent à constater lors de la recette pilote ; seules la logique pure et l’orchestration avec un faux client sont testées localement.
