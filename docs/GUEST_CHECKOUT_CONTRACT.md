## Identité et HTTP (première tranche parallèle)
- Supabase Phone OTP établit une identité sans mot de passe, réutilisée par les RLS actuelles ; aucun annuaire public téléphone+nom. Les noms sont des coordonnées, pas des secrets. Aucun transfert automatique d'anciens dossiers entre utilisateurs sur la seule égalité d'un téléphone non vérifié.
- POST `/api/auth/phone/start` strict `{phone, first_name, last_name, purpose: "booking"|"lookup"}`. Numéro normalisé E164 (Martinique0696/0697→+596, métropole06/07→+33, international+ accepté). Réponse200 `{status:"code_requested", kind:"sms"|"phone_change", retry_after:60, phone_suffix:string}` ; lookup d'un numéro inexistant même réponse générique sans affirmer SMS envoyé. Si sessionclient déjà vérifiée et même téléphone : `{status:"verified"}`. Sans session, signInWithOtp shouldCreateUser uniquement booking, metadata roleclient/noms. Sessionclient existante : updateUser phone (phone_change), jamais remplacement silencieux d'identité ; rôleprofessionnel refusé409. Fournisseur indisponible503, jamais faux succès ;429+Retry-After en caslimite.
- POST `/api/auth/phone/verify` strict `{phone, token, kind:"sms"|"phone_change"}`. Cookies Supabase SSR, aucun JWT enJSON. `sms` seulement hors session ; `phone_change` lié au même utilisateur client courant. GetUser+profil client et téléphone confirmé exact revérifiés avant200 `{verified:true}`. Code invalide422, indisponible503 ; pas de données métier dans réponse.
- GET `/api/auth/phone/session` privé `{authenticated:boolean, verified_phone:boolean, phone_suffix:string|null, role:string|null, email_account:boolean}` après getUser validé ; rien sur comptes tiers.
- POST `/api/auth/phone/upgrade` strict `{email,password}` facultatif APRÈS accès téléphone vérifié client ; updateUser mêmeUID, jamais nouveau compte/job/changementrole ; réponse200 `{confirmation_required:true}` sans annoncer réceptionemail. Comptes existants409 orienté profil, pas écrasement.
- Toutes réponses private,no-store ; erreurs provider neutres,503Retry-After2 ; origine contrôlée,corps bornés,ratewarmborné+limitations fournisseur,aucun lognuméro/code/tokens. Tests routes SDK injectés, refusrôles/sessionchangement/enumération/codewrong/transport.
