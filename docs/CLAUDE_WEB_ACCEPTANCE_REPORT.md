Prérequis : serveur Next de la révision intégrée servie en local (par ex. `http://localhost:3017`) et reliée au projet Supabase dédié ; fichier de credentials privé hors dépôt (forme `scripts/qa/credentials.example.json`, mode 0600) ; module `playwright` 1.64.x déjà installé hors dépôt avec sa révision Chromium en cache (sinon `--chromium-path`).

Lecture des résultats : `summary.md` (tableau par scénario, FATAL éventuel, non-preuves), `result.json` (étapes, preuves, réseau résumé, `routeErrors`, `fatal`, `sha_verified`, `target`), `events.ndjson` (diagnostic pas à pas), `run.log` (console redactée), `cleanup.json` (readback par table ; tout `fail` exige une intervention manuelle, code 3). ## 3 quinquies. Compte admin de cohorte et migration plateforme 014 (dernier super admin)

**Constat transmis par le pilote.** Le projet Supabase réel ne compte actuellement **aucun** super admin réel. La migration 014 (lot plateforme, pas encore appliquée) ajoute sur `profiles` une protection « dernier super admin ». La suite `admin-old-dossiers` crée un compte admin de cohorte (rôle `admin` posé par la clé service sur un compte Auth confirmé) puis le supprime au nettoyage : une fois 014 appliquée, ce compte serait le dernier admin et sa suppression (`profiles` puis Auth) serait **refusée** par la protection.

**Validité de la stratégie actuelle.** La stratégie « admin de cohorte créé puis supprimé » n'est valable **qu'avant l'application de 014**. Le pilote exécute la recette admin de base avant 014 ; la suite est conservée telle quelle pour cette fenêtre. Règles respectées : la protection n'est pas affaiblie, aucun admin fictif permanent n'est créé, aucun contournement par secret.

**Ce qui est implémenté dans cette révision (peu coûteux).** `manifest.created.admin_profiles` nomme les profils dont le rôle `admin` a été posé par le harnais (marqueur, pas une étape de suppression). Dans `runCleanup`, un échec sur `profiles` ou sur l'étape Auth qui vise un de ces identifiants n'est jamais `pass` : l'entrée garde le **texte exact** de l'erreur serveur (redacté), ajoute `admin_accounts: [ids]` et un rappel « si la suppression a été refusée par la protection dernier super admin (migration 014), la stratégie admin de cohorte ne s'applique plus ; compte à traiter manuellement » ; `cleanup.ok=false`, code `3`, `summary.md` « nettoyage incomplet ». Couvert par un test unitaire (`profiles` refusé avec readback 1, Auth refusé par message de garde, annotation présente ; sans admin dans le manifeste, aucune annotation). Comportement avant 014 inchangé (la suppression réussit, aucune annotation).

**Stratégie post-014 proposée (non implémentée, à décider par le pilote).**
1. *Préférée — scénarios admin hors Auth réel.* Exécuter les scénarios admin dans une **transaction SQL annulée** ou un schéma isolé (profil admin créé dans la transaction, lectures `admin_*` exercées par RPC/SQL, `rollback` final) : aucun compte admin réel n'existe jamais, la protection n'est jamais sollicitée. Limite : la partie navigateur de `admin-old-dossiers` (pagination « Dossiers par page », « Suivant », « Ouvrir ») suppose une session Auth réelle ; elle ne serait plus couverte par le harnais navigateur mais par les vérifications SQL/RPC du lot backend, ou par une recette manuelle avec un admin réel légitime.
2. *Repli — refus explicite, jamais un PASS.* Quand la protection est détectée, la suite admin se termine avec un résultat dédié « **non exécutable après 014 : stratégie à définir** » (nouveau statut de scénario `BLOCKED` dans `report.mjs`, distinct de PASS/FAIL/ANOMALY, affiché dans `summary.md` et `result.json`, code de sortie inchangé car ce n'est ni un défaut ni un plantage), sans créer le compte admin. Détection proposée **par lecture inoffensive** : la migration 014 devrait exposer un marqueur lisible par la clé service sans effet de bord (par exemple une vue `public.platform_guards` ou une ligne de réglage listant `last_super_admin_guard: true`), lue dans le préflight de la suite ; à défaut, la présence du trigger n'est pas observable par PostgREST (ni `pg_trigger` ni `information_schema` ne sont exposés) et un drapeau explicite `--admin-guard applied` passé par le pilote forcerait le refus. Dans les deux cas, aucune tentative de création d'admin, aucun secret supplémentaire.
3. *Exclu.* Créer un admin fictif permanent ; désactiver ou contourner le trigger pendant la recette ; supprimer via SQL direct en contournant la protection.

Décision attendue du pilote : option 1 ou 2 (ou les deux : 1 pour la couverture, 2 comme garde-fou du harnais), et la forme du marqueur de détection si l'option 2 est retenue.

**Mise en œuvre retenue (décision pilote) — préflight admin.** Le propriétaire active le **premier super administrateur réel** (compte réel, activé par le pilote ; aucun mot de passe manipulé par quiconque, aucun admin fictif). Dès qu'un super admin réel existe, la garde 014 ne bloque plus la suppression de l'admin de cohorte. `scripts/qa/lib/admin-preflight.mjs` : `adminPreflight(db, manifest)` compte, avec la clé service et en lecture seule (un `HEAD count=exact` sur `profiles`, filtre `role=eq.admin` + `id=not.in.(<ids de cohorte>)`), les super admins réels ; `>= 1` → la suite `admin-old-dossiers` enregistre un scénario PASS « admin-preflight » puis crée son admin de cohorte ; `0` → `report.blocked(...)` : statut **`BLOCKED`** avec la raison exacte « suite admin non exécutable : aucun super administrateur réel, la garde 014 bloquerait le nettoyage », **rien n'est créé**, la suite retourne ; `BLOCKED` est compté à part dans `summary.blocked`, affiché dans `summary.md`, et **ne change pas le code de sortie** (toujours décidé par FAIL/FATAL/nettoyage des autres suites). Jamais de lecture de données, de modification, de bannissement ni de suppression d'un admin hors cohorte : le plan de nettoyage ne vise que les identifiants du manifeste (test `admin-preflight.test.mjs` : aucune valeur de filtre hors manifeste, `admin_profiles` n'est jamais une étape de suppression). Le marqueur `admin_profiles` et la règle « suppression refusée → INCOMPLETE » restent en place comme second filet. L'admin de cohorte est supprimé au nettoyage **tandis que le super admin réel demeure** (il n'est jamais ciblé). Tests unitaires à faux client : compte 0 → BLOCKED, aucune création, code de sortie inchangé ; compte 1 → la suite poursuit jusqu'à la création de son admin ; filtre d'exclusion de cohorte ; un seul appel `count`, jamais `select/update/delete` sur un admin.

Commande pilote pour la suite admin seule (après activation du super admin réel) :

```
QA_PLAYWRIGHT_PATH=<module playwright> node scripts/qa/run.mjs --base-url http://localhost:<port> --sha <SHA servi> --project <ref dédié> --credentials <json 0600> --app-dir <checkout servi> --suite admin-old-dossiers --timeout-ms 120000 --json
```

Lecture attendue : `result.json` → scénario `admin-preflight` PASS avec `realAdmins >= 1`, puis le scénario de pagination ; `cleanup.json` → étapes `profiles` et Auth `pass`, readback 0 (le compte réel n'y figure pas) ; en l'absence de super admin réel : un seul scénario `BLOCKED`, `manifest.json` sans identifiant, code de sortie 0 si aucune autre suite n'échoue.
